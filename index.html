01What is Git?

Git saves snapshots of your project folder. Each snapshot is called a commit. Think of it as a save point in a video game: you can look back, compare, or go back.

  • Git is a tool on your computer.
  • GitHub is a website that keeps a copy of your commits online. It's your backup, and other people (or Vercel) can get your code from it.

02The 4 places your work lives

Your filesthe folder you edit
git add→
Staging areachanges picked for the next save
git commit→
Your historysaves on your computer (.git folder)
git push→
GitHubthe online copy, called origin

⟵ git pull brings new saves from GitHub back to your computer.

Moving-day picture: git add = put things in a box. git commit = close the box and write a label on it. git push = ship the box.

03Setup (only once)

Tell Git your name and email. They appear on every commit you make.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Then either start a new project in the current folder…

git init

…or download a project that's already on GitHub:

git clone https://github.com/your-name/your-project.git

04Your daily loop

These five commands cover about 90% of everyday Git.

  1. See what changed

    git status

    Lists the files you changed, and which ones are staged.

  2. Pick the changes to save

    git add .              # everything
git add index.html     # or just one file

  3. Save them, with a short note

    git commit -m "Fix export button"

    Write what the change does. "Fix export button" helps later. "stuff" doesn't.

  4. Send your saves to GitHub

    git push

  5. Get saves made somewhere else

    git pull

    Do this first when you start working on another computer.

05Looking around

CommandShows you
git statusWhat changed and what's staged
git log --onelineYour past saves, one line each
git diffThe exact lines you changed but didn't stage yet
git diff --stagedThe exact lines you staged
git show a1b2c3dEverything inside one commit

Press q to leave a long list like git log.

06Branches

A branch is a separate line of work. You can try something without touching main, your real version. When it works, you merge it back.

git branch                    # list branches (* = the one you're on)
git switch -c fix-something   # make a new branch and go to it
git switch main               # go back to main
git merge fix-something       # bring the branch's work into main
git branch -d fix-something   # delete it once it's merged

-d (small d) is safe: Git refuses if the branch has work that isn't merged yet. -D (big D) deletes anyway.

07When two changes clash (merge conflict)

If two branches change the same line, Git can't guess which one to keep. It marks the spot in the file and asks you:

<<<<<<< HEAD
<h1>Welcome</h1>        ← your version (main)
=======
<h1>Hello there</h1>    ← the other branch's version
>>>>>>> fix-something

To fix it:

  1. Edit the file so it says what you want.
  2. Delete the <<<, === and >>> lines.
  3. Save the file, then run git add . and git commit.

It looks scary the first time, but it's only a text edit.

08Undoing things

I want to…CommandSafe?
Unstage a file (keep my edits)git restore --staged file.txtYes
Fix the message of my last commit, not pushed yetgit commit --amend -m "Better"Yes, before push
Cancel an old commit that's already on GitHubgit revert a1b2c3dYes: adds a new commit that does the opposite
Throw away my unsaved edits to one filegit restore file.txtEdits are gone
Make my folder exactly like GitHubgit reset --hard origin/mainThrows away everything local

09The .gitignore file

A file named .gitignore lists things Git should never save. One per line:

node_modules/
.env
.DS_Store

Never commit passwords or API keys. Keep them in .env and put .env in .gitignore. Once a key is pushed to GitHub, treat it as leaked: change the key.

10Why changing an old commit needs a force push

This is what happened when we removed the Co-Authored-By: Claude lines from your projects.

Every commit has an ID like ed6363b. Git builds that ID from:

  • the files
  • the message
  • the author and date
  • the ID of the commit before it

So if you change one word in an old message, that commit gets a new ID. The next commit contains the old ID of its parent, so its ID changes too. And so on. Every commit after the change gets a new ID.

Now GitHub and your computer disagree. A normal git push gets rejected, because Git thinks you're about to lose GitHub's commits. A force push says: "replace your copy with mine."

git push --force-with-lease

--force-with-lease is the careful kind of force. It stops if someone else pushed new work since you last looked.

After a force push, other copies of the project (on another computer, for example) are out of date. To fix one, run this on that computer. It throws away any local changes there:

git fetch
git reset --hard origin/main

11Danger zone

Stop and think before you run any of these:

CommandWhat it destroys
git push --forceHistory on GitHub
git reset --hardChanges you haven't committed
git clean -fdFiles Git isn't tracking
Deleting the .git folderAll history on that computer

Simple rule: if a command says --force or --hard, copy your project folder somewhere first.

13Quick quiz

1. You changed some files. Which command lists them?

git status shows what changed and what's staged.

2. What does git add do?

It puts changes in the staging area. Nothing is saved until you commit.

3. You committed, but GitHub doesn't show your change. What did you forget?

A commit only lives on your computer until you push it.

4. What's the safest way to undo a commit that's already on GitHub?

git revert adds a new commit that cancels the old one. History stays intact.

5. Why did removing a line from an old commit message need a force push?

Each ID includes the ID of the commit before it, so one change ripples forward.

6. Which file should never be committed?

Secrets go in .env, and .env goes in .gitignore.

01C'est quoi Git ?

Git enregistre des instantanés du dossier de ton projet. Chaque instantané s'appelle un commit. Pense à un point de sauvegarde dans un jeu vidéo : tu peux regarder en arrière, comparer, ou revenir.

  • Git est un outil sur ton ordinateur.
  • GitHub est un site web qui garde une copie de tes commits en ligne. C'est ta sauvegarde, et d'autres personnes (ou Vercel) peuvent y récupérer ton code.

L'image du déménagement : git add = mettre des affaires dans un carton. git commit = fermer le carton et écrire une étiquette dessus. git push = expédier le carton.

03Installation (une seule fois)

git config --global user.email "toi@exemple.com"

Ensuite, soit tu démarres un nouveau projet dans le dossier actuel…

git init

…soit tu télécharges un projet qui est déjà sur GitHub :

git clone https://github.com/ton-nom/ton-projet.git

04Ta routine quotidienne

Ces cinq commandes couvrent environ 90 % de l'usage courant de Git.

  1. Voir ce qui a changé

    git status

    Liste les fichiers modifiés, et ceux qui sont en staging.

  2. Choisir les changements à sauvegarder

    git add .              # tout
git add index.html     # ou un seul fichier

  3. Les sauvegarder, avec une courte note

    git commit -m "Corrige le bouton d'export"

    Écris ce que fait le changement. « Corrige le bouton d'export » aide plus tard. « truc » non.

  4. Envoyer tes sauvegardes sur GitHub

    git push

  5. Récupérer les sauvegardes faites ailleurs

    git pull

    Fais-le en premier quand tu commences à travailler sur un autre ordinateur.

05Regarder autour de soi

06Les branches

Une branche est une ligne de travail séparée. Tu peux essayer quelque chose sans toucher à main, ta vraie version. Quand ça marche, tu la fusionnes (merge).

git branch                    # liste les branches (* = celle où tu es)
git switch -c fix-something   # crée une nouvelle branche et va dessus
git switch main               # retourne sur main
git merge fix-something       # ramène le travail de la branche dans main
git branch -d fix-something   # la supprime une fois fusionnée

-d (d minuscule) est sûr : Git refuse si la branche contient du travail pas encore fusionné. -D (D majuscule) supprime quand même.

07Quand deux changements se heurtent (conflit de fusion)

Si deux branches modifient la même ligne, Git ne peut pas deviner laquelle garder. Il marque l'endroit dans le fichier et te demande :

<<<<<<< HEAD
<h1>Bienvenue</h1>        ← ta version (main)
=======
<h1>Salut toi</h1>        ← la version de l'autre branche
>>>>>>> fix-something

Pour le résoudre :

  1. Modifie le fichier pour qu'il dise ce que tu veux.
  2. Supprime les lignes <<<, === et >>>.
  3. Enregistre le fichier, puis lance git add . et git commit.

Ça fait peur la première fois, mais ce n'est qu'une modification de texte.

09Le fichier .gitignore

Un fichier nommé .gitignore liste ce que Git ne doit jamais sauvegarder. Un élément par ligne :

node_modules/
.env
.DS_Store

Ne commite jamais de mots de passe ou de clés d'API. Garde-les dans .env et mets .env dans .gitignore. Une fois une clé poussée sur GitHub, considère-la comme divulguée : change la clé.

10Pourquoi modifier un vieux commit demande un force push

C'est ce qui s'est passé quand on a retiré les lignes Co-Authored-By: Claude de tes projets.

Chaque commit a un ID comme ed6363b. Git construit cet ID à partir de :

  • les fichiers
  • le message
  • l'auteur et la date
  • l'ID du commit précédent

Donc si tu changes un mot dans un vieux message, ce commit reçoit un nouvel ID. Le commit suivant contient l'ancien ID de son parent, donc son ID change aussi. Et ainsi de suite. Chaque commit après le changement reçoit un nouvel ID.

Maintenant GitHub et ton ordinateur ne sont plus d'accord. Un git push normal est rejeté, car Git pense que tu vas perdre les commits de GitHub. Un force push dit : « remplace ta copie par la mienne. »

git push --force-with-lease

--force-with-lease est la version prudente du force. Il s'arrête si quelqu'un d'autre a poussé du nouveau travail depuis ta dernière vérification.

Après un force push, les autres copies du projet (sur un autre ordinateur, par exemple) sont périmées. Pour en réparer une, lance ceci sur cet ordinateur. Ça jette toutes les modifs locales qui s'y trouvent :

git fetch
git reset --hard origin/main

11Zone dangereuse

Arrête-toi et réfléchis avant de lancer l'une de ces commandes :

Règle simple : si une commande contient --force ou --hard, copie d'abord ton dossier de projet ailleurs.

Working with GitHub, fixing mistakes, and shipping versions.

01Fetch vs pull

In chapter 1 you used git pull. It actually does two things in a row:

GitHubthe online copy
git fetch→
origin/mainyour copy of what GitHub had, last time you checked
git merge→
mainyour own branch, the one you edit

git pull = git fetch + git merge

  • git fetch only downloads. Your files don't change. It's safe any time.
  • git pull downloads and mixes it into your work.

Fetch first when you want to look before you mix:

git fetch
git log --oneline main..origin/main   # commits GitHub has that you don't
git pull                              # happy? now bring them in

02Stash: put work aside for a moment

You're halfway through a change. Suddenly you need to fix a bug on main. Your work isn't ready to commit. Stash it: Git puts it on a shelf and gives you a clean folder.

git stash              # shelve my unfinished changes
git switch main        # go fix the bug, commit, push…
git switch my-branch   # come back
git stash pop          # take my changes off the shelf
CommandDoes
git stash -uAlso shelves new files Git doesn't track yet
git stash listShows what's on the shelf
git stash dropThrows away the top item on the shelf

03Pull requests

A pull request (PR) is a page on GitHub that says: "here's my branch, please review it and merge it into main." It's how teams work, and it's useful alone too.

  1. Make a branch

    git switch -c add-pdf-export

  2. Work and commit as usual

    git add, git commit, as many times as you like.

  3. Push the branch

    git push -u origin add-pdf-export

    -u links your branch to GitHub's, so next time a plain git push is enough.

  4. Open the pull request

    GitHub shows a Compare & pull request button. Or, with GitHub's gh tool:

    gh pr create --fill

  5. Review

    Read the changes on the PR page. If something needs fixing, just commit and push again: the PR updates by itself.

  6. Merge, then clean up

    Click Merge on GitHub. Then on your computer:

    git switch main
git pull
git branch -d add-pdf-export

Why bother when you work alone? You get one page that shows the whole change before it lands. And if the project is connected to Vercel, each PR gets its own preview link to try.

04Merge vs rebase

Your branch started from B. Meanwhile main got a new commit, C. There are two ways to combine them.

git switch my-branch
git rebase main

If it stops on a conflict: fix the file, then git add . and git rebase --continue. Changed your mind? git rebase --abort puts everything back.

Golden rule: only rebase commits that are only on your computer. Rebasing commits you already pushed means a force push.

A handy everyday version: git pull --rebase puts your unpushed commits on top of what you just downloaded, so you don't get a merge commit each time you pull.

05Fix your last commit

Forgot a file, or made a typo in the message? Change the last commit instead of making a new one:

git add forgotten.css
git commit --amend --no-edit           # add the file, keep the message
git commit --amend -m "Better message" # or change the message

Amend makes a new commit with a new ID. Only do it before you push.

06Cherry-pick: copy one commit

A fix sits on another branch and you want just that one commit here, not the whole branch:

git switch main
git cherry-pick a1b2c3d

Git copies that commit onto main. Find its ID with git log --oneline other-branch.

07Tags and versions

A tag is a name stuck on one commit, like v1.1.0. Your des-doublons and print-gen projects already use them. Tags mark "this is the version people got."

git tag -a v1.2.0 -m "Add PDF export"   # tag the current commit
git push origin v1.2.0                  # send the tag to GitHub
git tag                                 # list tags

Gotcha: a plain git push does not send tags. Push each tag by name, or all of them with git push --tags.

What the three numbers mean

From 1.1.0 to…When
1.1.1Patch: you fixed a bug
1.2.0Minor: you added a feature, nothing breaks (like des-doublons adding .xlsx support in 1.1.0)
2.0.0Major: something old stops working the way it did

Want a Release page on GitHub with notes and downloads? gh release create v1.2.0 --generate-notes

08Detective tools

CommandAnswers
git log --oneline --graph --allWhat do all my branches look like? (draws them)
git log -p index.htmlHow has this one file changed over time?
git blame index.htmlWhich commit last changed each line?
git log -S "dark mode"Which commits added or removed this text?
git show a1b2c3dWhat's inside this one commit?

09The safety net: reflog

You ran git reset --hard or deleted a branch, and a commit seems gone. Don't panic. Git keeps a diary of every place your branch has pointed to:

git reflog
a03e767 HEAD@{0}: reset: moving to origin/main
9f8e7d6 HEAD@{1}: commit: Add dark mode        ← the "lost" commit
ed6363b HEAD@{2}: commit: Fix export button

Found it? Put it on a new branch, so nothing else gets touched:

git branch rescue 9f8e7d6
git switch rescue

The reflog only knows about commits. Changes you never committed can't be rescued this way. One more reason to commit often. Lost commits usually stay findable for about 30 days.

10Good commit messages

Some of your projects already start messages with a small label, like feat: or fix:. That's a common habit called Conventional Commits:

LabelUse it forExample
feat:A new featurefeat: add PDF export
fix:A bug fixfix: keep RTL word order in export
docs:Only the README or docsdocs: add install steps
refactor:Same behavior, cleaner coderefactor: split the parser
chore:Housekeepingchore: update dependencies

Three tips: keep the first line under about 50 characters, write it like an order ("add", not "added"), and say what changed, not "update".

11Shortcuts (aliases)

Tired of typing long commands? Give them short names, once:

git config --global alias.st status
git config --global alias.lg "log --oneline --graph --all"

Now git st and git lg work everywhere on this computer.

13Quick quiz

1. What's the difference between git fetch and git pull?

git pull = git fetch + git merge.

2. You're halfway through a change and need to switch branches right now. What do you use?

Stash shelves your unfinished work. git stash pop brings it back.

3. What's the golden rule of rebase?

Rebased commits get new IDs, so rebasing pushed work means a force push.

4. After a git reset --hard, a commit seems gone. Where do you look?

The reflog lists everywhere your branch has been, including that commit.

5. You ran git push, but your new tag v1.3 isn't on GitHub. Why?

Use git push origin v1.3 or git push --tags.

6. Version 1.1.0 had a bug. You fixed it. What's the new version?

A bug fix bumps the last number: the patch.

git fetch

02Stash : mettre son travail de côté un instant

Tu es à mi-chemin d'un changement. Soudain, tu dois corriger un bug sur main. Ton travail n'est pas prêt à être commité. Fais un stash : Git le pose sur une étagère et te donne un dossier propre.

git stash              # met mes changements inachevés de côté
git switch main        # va corriger le bug, commit, push…
git switch my-branch   # reviens
git stash pop          # reprends mes changements sur l'étagère

03Pull requests

Une pull request (PR) est une page sur GitHub qui dit : « voici ma branche, relis-la et fusionne-la dans main, s'il te plaît. » C'est la façon de travailler en équipe, et c'est utile aussi tout seul.

  1. Crée une branche

    git switch -c add-pdf-export

  2. Travaille et commite comme d'habitude

    git add, git commit, autant de fois que tu veux.

  3. Pousse la branche

    git push -u origin add-pdf-export

    -u relie ta branche à celle de GitHub, donc la prochaine fois un simple git push suffit.

  4. Ouvre la pull request

    GitHub affiche un bouton Compare & pull request. Ou, avec l'outil gh de GitHub :

    gh pr create --fill

  5. Relis

    Lis les changements sur la page de la PR. Si quelque chose doit être corrigé, commite et pousse à nouveau : la PR se met à jour toute seule.

  6. Fusionne, puis nettoie

    Clique sur Merge sur GitHub. Ensuite, sur ton ordinateur :

    git switch main
git pull
git branch -d add-pdf-export

Pourquoi s'embêter quand on travaille seul ? Tu obtiens une page qui montre tout le changement avant qu'il n'arrive. Et si le projet est connecté à Vercel, chaque PR a son propre lien d'aperçu à essayer.

04Merge vs rebase

Ta branche est partie de B. Entre-temps, main a reçu un nouveau commit, C. Il y a deux façons de les combiner.

git switch my-branch
git rebase main

S'il s'arrête sur un conflit : corrige le fichier, puis git add . et git rebase --continue. Tu as changé d'avis ? git rebase --abort remet tout en place.

Règle d'or : ne rebase que des commits qui sont uniquement sur ton ordinateur. Rebaser des commits déjà poussés oblige à faire un force push.

Une version pratique au quotidien : git pull --rebase place tes commits non poussés par-dessus ce que tu viens de télécharger, pour ne pas avoir un commit de fusion à chaque pull.

05Corriger ton dernier commit

Tu as oublié un fichier, ou fait une faute dans le message ? Modifie le dernier commit au lieu d'en faire un nouveau :

git add forgotten.css
git commit --amend --no-edit           # ajoute le fichier, garde le message
git commit --amend -m "Meilleur message" # ou change le message

Amend crée un nouveau commit avec un nouvel ID. Ne le fais qu'avant de pousser.

06Cherry-pick : copier un seul commit

Un correctif se trouve sur une autre branche et tu veux juste ce commit ici, pas toute la branche :

git switch main
git cherry-pick a1b2c3d

Git copie ce commit sur main. Trouve son ID avec git log --oneline other-branch.

07Tags et versions

Un tag est un nom collé sur un commit, comme v1.1.0. Tes projets des-doublons et print-gen en utilisent déjà. Les tags marquent « voici la version que les gens ont reçue ».

git tag -a v1.2.0 -m "Ajoute l'export PDF"   # tagge le commit actuel
git push origin v1.2.0                       # envoie le tag sur GitHub
git tag                                      # liste les tags

Piège : un simple git push n'envoie pas les tags. Pousse chaque tag par son nom, ou tous avec git push --tags.

Ce que veulent dire les trois nombres

De 1.1.0 vers…Quand
1.1.1Patch : tu as corrigé un bug
1.2.0Mineure : tu as ajouté une fonctionnalité, rien ne casse (comme des-doublons qui ajoute le support .xlsx en 1.1.0)
2.0.0Majeure : quelque chose d'ancien ne marche plus comme avant

Tu veux une page Release sur GitHub avec notes et téléchargements ? gh release create v1.2.0 --generate-notes

09Le filet de sécurité : reflog

Tu as lancé git reset --hard ou supprimé une branche, et un commit semble perdu. Pas de panique. Git tient un journal de tous les endroits où ta branche a pointé :

git reflog
a03e767 HEAD@{0}: reset: moving to origin/main
9f8e7d6 HEAD@{1}: commit: Add dark mode        ← le commit « perdu »
ed6363b HEAD@{2}: commit: Fix export button

Tu l'as trouvé ? Mets-le sur une nouvelle branche, pour ne rien toucher d'autre :

git branch rescue 9f8e7d6
git switch rescue

Le reflog ne connaît que les commits. Les changements que tu n'as jamais commités ne peuvent pas être sauvés ainsi. Une raison de plus de commiter souvent. Les commits perdus restent généralement retrouvables environ 30 jours.

10De bons messages de commit

Certains de tes projets commencent déjà leurs messages par une petite étiquette, comme feat: ou fix:. C'est une habitude courante appelée Conventional Commits :

ÉtiquetteÀ utiliser pourExemple
feat:Une nouvelle fonctionnalitéfeat: add PDF export
fix:Un correctif de bugfix: keep RTL word order in export
docs:Seulement le README ou la docdocs: add install steps
refactor:Même comportement, code plus proprerefactor: split the parser
chore:Tâches d'entretienchore: update dependencies

Trois conseils : garde la première ligne sous 50 caractères environ, écris-la comme un ordre (« add », pas « added »), et dis ce qui a changé, pas juste « update ».

11Raccourcis (alias)

Fatigué de taper de longues commandes ? Donne-leur des noms courts, une seule fois :

git config --global alias.st status
git config --global alias.lg "log --oneline --graph --all"

Maintenant git st et git lg marchent partout sur cet ordinateur.

13Petit quiz

1. Quelle est la différence entre git fetch et git pull ?

git pull = git fetch + git merge.

2. Tu es à mi-chemin d'un changement et tu dois changer de branche tout de suite. Que utilises-tu ?

Stash met ton travail inachevé de côté. git stash pop te le rend.

3. Quelle est la règle d'or du rebase ?

Les commits rebasés reçoivent de nouveaux IDs, donc rebaser du travail poussé oblige à un force push.

4. Après un git reset --hard, un commit semble disparu. Où regardes-tu ?

Le reflog liste tous les endroits où ta branche est passée, y compris ce commit.

5. Tu as lancé git push, mais ton nouveau tag v1.3 n'est pas sur GitHub. Pourquoi ?

Utilise git push origin v1.3 ou git push --tags.

6. La version 1.1.0 avait un bug. Tu l'as corrigé. Quelle est la nouvelle version ?

Un correctif de bug augmente le dernier nombre : le patch.

Git power tools

Cleaning up history, hunting bugs, and making Git work for you.

Clean up commitsOld file versionBisect WorktreeSubmodulesHooks Leaked a secret?Cheat sheetQuiz

01Clean up commits before you share them

Your branch has messy commits like "wip", "oops", "fix typo". Before you push, you can tidy them with an interactive rebase:

git rebase -i HEAD~3      # work on the last 3 commits

Git opens a text file with one line per commit, oldest first:

pick   a1b2c3d Add PDF export
squash d4e5f6a wip
squash 9f8e7d6 oops, fix typo

Change the word at the start of each line, save, and close the file:

WordDoes
pickKeep the commit as it is
squashMelt it into the commit above (you then write one combined message)
rewordKeep it, but change its message
dropDelete the commit

The example above turns three commits into one clean "Add PDF export".

Same golden rule as chapter 2: only for commits you haven't pushed. Every commit you touch gets a new ID.

The file opens in a terminal editor. If it's vim: press i to type, then Esc, then type :wq and Enter to save and quit. To use VS Code instead, run once: git config --global core.editor "code --wait"

02Get an old version of one file

You broke style.css and want it back as it was in an older commit, without touching anything else:

git log --oneline style.css                  # find the commit you want
git restore --source=a1b2c3d style.css       # bring that version back

Just want to look at it without changing anything?

git show a1b2c3d:style.css

03Bisect: find the commit that broke something

Something worked last week. Now it's broken. There are 100 commits in between. Which one did it? Bisect finds it by halving the list again and again, like guessing a number between 1 and 100: about 7 tests instead of 100.

  1. Start

    git bisect start
git bisect bad              # the current version is broken
git bisect good v1.2.0      # this old version worked

  2. Test what Git gives you

    Git switches your files to a commit in the middle. Open the app and try it. Then tell Git:

    git bisect good     # works here
git bisect bad      # broken here

    Repeat until Git prints "a1b2c3d is the first bad commit".

  3. Go back to normal

    git bisect reset

Have a test that checks it? Let Git do every step by itself: git bisect run npm test

04Worktree: two branches open at once

Normally one folder shows one branch. Switching means stashing or committing first. A worktree gives you a second folder for another branch, sharing the same history:

git worktree add ../print-gen-hotfix main     # new folder, on main
cd ../print-gen-hotfix                        # fix, commit, push there
git worktree list                             # see all your folders
git worktree remove ../print-gen-hotfix       # done: remove the extra folder

Handy when you're in the middle of a big change and an urgent fix comes in. Your half-done work stays exactly where it was.

One branch can only be open in one folder at a time. Git will tell you if you try twice.

05Submodules: a project inside a project

A submodule is another Git project placed in a folder of yours, pinned to one exact commit. Used for shared code or libraries you don't want to copy in.

git submodule add https://github.com/someone/lib.git lib   # add one
git clone --recurse-submodules URL                         # clone with submodules
git submodule update --init                                # forgot? fill them in now

Submodules confuse people: a plain clone leaves their folders empty, and after you update one you must commit the new pin in the main project. If a normal package (npm, Swift Package) can do the job, use that instead.

06Hooks: scripts Git runs for you

A hook is a small script Git runs at a moment you choose, for example right before each commit. If the script fails, the commit is stopped.

Example: never let a .env file get committed by accident. Create the file .git/hooks/pre-commit:

#!/bin/sh
if git diff --cached --name-only | grep -q '\.env$'; then
  echo "Stop: you're about to commit a .env file."
  exit 1
fi

Then make it runnable:

chmod +x .git/hooks/pre-commit
HookRunsGood for
pre-commitBefore each commitLint, format, block secrets
commit-msgAfter you write the messageCheck it starts with feat:/fix:
pre-pushBefore each pushRun the tests

Files in .git/hooks are not pushed to GitHub. To share hooks, keep them in a normal folder (say hooks/) and run git config core.hooksPath hooks in each copy. JavaScript projects often use a tool called husky for this. Skip a hook once with git commit --no-verify.

07Pushed a secret by mistake?

This is the same tool we used to remove the co-author lines: git filter-repo. It rewrites the whole history.

  1. Change the secret first

    Make a new key and turn the old one off, at the service it came from. Bots scan GitHub for keys within minutes, so assume it's already been seen. This is the step that actually protects you.

  2. Remove the file from every commit

    git filter-repo --path .env --invert-paths

    --invert-paths means "keep everything except this path". It also removes origin as a safety measure, so add it back:

    git remote add origin https://github.com/your-name/your-project.git

  3. Force-push and stop it coming back

    git push --force origin main
echo ".env" >> .gitignore

Copy the project folder before running filter-repo. And like any force push, every other copy of the project must be reset afterwards (chapter 1, section 10).

09Quick quiz

1. In an interactive rebase, which word melts a commit into the one above it?

squash combines commits. drop deletes one.

2. There are 100 commits between "worked" and "broken". About how many tests does bisect need?

Each test cuts the list in half: 100 → 50 → 25 → 13 → 7 → 4 → 2 → 1.

3. You need main open while your branch stays as it is. What's the cleanest tool?

A worktree is a second folder that shares the same history.

4. You cloned a project but its lib/ folder is empty. Why?

Run git submodule update --init, or clone with --recurse-submodules.

5. You made a pre-commit hook and pushed. Does your other computer get it?

Share hooks through a normal folder plus core.hooksPath, or a tool like husky.

6. You pushed an API key to GitHub. What's the most important step?

Once pushed, assume it was seen. Rewriting history helps, but only a new key really protects you.

Les outils avancés de Git

Nettoyer l'historique, traquer les bugs et faire travailler Git pour toi.

Nettoyer les commitsAncienne version d'un fichierBisect WorktreeSous-modulesHooks Un secret divulgué ?Aide-mémoireQuiz

01Nettoyer les commits avant de les partager

Ta branche contient des commits brouillons comme « wip », « oops », « fix typo ». Avant de pousser, tu peux les ranger avec un rebase interactif :

git rebase -i HEAD~3      # travaille sur les 3 derniers commits

Git ouvre un fichier texte avec une ligne par commit, le plus ancien en premier :

pick   a1b2c3d Add PDF export
squash d4e5f6a wip
squash 9f8e7d6 oops, fix typo

Change le mot au début de chaque ligne, enregistre, et ferme le fichier :

MotFait
pickGarde le commit tel quel
squashLe fond dans le commit du dessus (tu écris ensuite un seul message combiné)
rewordLe garde, mais change son message
dropSupprime le commit

L'exemple ci-dessus transforme trois commits en un seul « Add PDF export » propre.

Même règle d'or qu'au chapitre 2 : seulement pour des commits non poussés. Chaque commit touché reçoit un nouvel ID.

Le fichier s'ouvre dans un éditeur de terminal. Si c'est vim : appuie sur i pour écrire, puis Esc, puis tape :wq et Entrée pour enregistrer et quitter. Pour utiliser VS Code à la place, lance une fois : git config --global core.editor "code --wait"

02Récupérer une ancienne version d'un fichier

Tu as cassé style.css et tu veux le retrouver tel qu'il était dans un ancien commit, sans toucher au reste :

git log --oneline style.css                  # trouve le commit voulu
git restore --source=a1b2c3d style.css       # ramène cette version

Tu veux juste la regarder sans rien changer ?

git show a1b2c3d:style.css

03Bisect : trouver le commit qui a tout cassé

Quelque chose marchait la semaine dernière. Maintenant c'est cassé. Il y a 100 commits entre les deux. Lequel est le coupable ? Bisect le trouve en coupant la liste en deux encore et encore, comme deviner un nombre entre 1 et 100 : environ 7 tests au lieu de 100.

  1. Démarrer

    git bisect start
git bisect bad              # la version actuelle est cassée
git bisect good v1.2.0      # cette ancienne version marchait

  2. Tester ce que Git te donne

    Git place tes fichiers sur un commit du milieu. Ouvre l'app et essaie. Puis dis à Git :

    git bisect good     # ça marche ici
git bisect bad      # c'est cassé ici

    Répète jusqu'à ce que Git affiche « a1b2c3d is the first bad commit ».

  3. Revenir à la normale

    git bisect reset

Tu as un test qui vérifie ça ? Laisse Git faire toutes les étapes tout seul : git bisect run npm test

04Worktree : deux branches ouvertes en même temps

Normalement, un dossier montre une branche. Changer veut dire faire un stash ou un commit d'abord. Un worktree te donne un second dossier pour une autre branche, avec le même historique :

git worktree add ../print-gen-hotfix main     # nouveau dossier, sur main
cd ../print-gen-hotfix                        # corrige, commit, push là-bas
git worktree list                             # voir tous tes dossiers
git worktree remove ../print-gen-hotfix       # fini : supprime le dossier en plus

Pratique quand tu es au milieu d'un gros changement et qu'un correctif urgent arrive. Ton travail à moitié fait reste exactement où il était.

Une branche ne peut être ouverte que dans un seul dossier à la fois. Git te le dira si tu essaies deux fois.

05Sous-modules : un projet dans un projet

Un sous-module est un autre projet Git placé dans un dossier du tien, épinglé sur un commit précis. On l'utilise pour du code partagé ou des bibliothèques que tu ne veux pas copier.

git submodule add https://github.com/someone/lib.git lib   # en ajouter un
git clone --recurse-submodules URL                         # cloner avec les sous-modules
git submodule update --init                                # oublié ? remplis-les maintenant

Les sous-modules embrouillent les gens : un clone simple laisse leurs dossiers vides, et après en avoir mis un à jour, tu dois commiter la nouvelle épingle dans le projet principal. Si un paquet normal (npm, Swift Package) peut faire le travail, utilise-le plutôt.

06Hooks : des scripts que Git lance pour toi

Un hook est un petit script que Git lance au moment de ton choix, par exemple juste avant chaque commit. Si le script échoue, le commit est bloqué.

Exemple : ne jamais laisser un fichier .env être commité par accident. Crée le fichier .git/hooks/pre-commit :

#!/bin/sh
if git diff --cached --name-only | grep -q '\.env$'; then
  echo "Stop: you're about to commit a .env file."
  exit 1
fi

Puis rends-le exécutable :

chmod +x .git/hooks/pre-commit
HookSe lanceUtile pour
pre-commitAvant chaque commitLint, formatage, bloquer les secrets
commit-msgAprès l'écriture du messageVérifier qu'il commence par feat:/fix:
pre-pushAvant chaque pushLancer les tests

Les fichiers de .git/hooks ne sont pas poussés sur GitHub. Pour partager des hooks, garde-les dans un dossier normal (par exemple hooks/) et lance git config core.hooksPath hooks dans chaque copie. Les projets JavaScript utilisent souvent un outil appelé husky pour ça. Ignore un hook une fois avec git commit --no-verify.

07Un secret poussé par erreur ?

C'est le même outil que celui qu'on a utilisé pour retirer les lignes co-auteur : git filter-repo. Il réécrit tout l'historique.

  1. Change d'abord le secret

    Crée une nouvelle clé et désactive l'ancienne, sur le service d'où elle vient. Des robots scannent GitHub à la recherche de clés en quelques minutes, donc suppose qu'elle a déjà été vue. C'est l'étape qui te protège vraiment.

  2. Retire le fichier de chaque commit

    git filter-repo --path .env --invert-paths

    --invert-paths veut dire « garde tout sauf ce chemin ». Il retire aussi origin par mesure de sécurité, donc remets-le :

    git remote add origin https://github.com/ton-nom/ton-projet.git

  3. Force push, et empêche le retour

    git push --force origin main
echo ".env" >> .gitignore

Copie le dossier du projet avant de lancer filter-repo. Et comme pour tout force push, chaque autre copie du projet doit ensuite être réinitialisée (chapitre 1, section 10).
